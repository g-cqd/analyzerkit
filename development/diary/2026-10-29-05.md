## 0039, by elimination

The test said "escaped keys allocate per key". Measured, with allocations counted on the measuring thread only:

| 500 keys | strict, no duplicate check | `.throwError` |
| --- | ---: | ---: |
| plain | 3 | 2,010 |
| `\u006b…` | 2,003 | 4,011 |
| `k\n…` | 3 | 2,011 |

Duplicate detection was innocent (one allocation for the reused buffer, as its comment says). Every `\u` escape in any
string costs four, inside `TapeBuilder.build()`, strict or not. One false lead on the way: a first harness measured
9,000 allocations for 4,000 `Hex.value` calls, but iterating an array inside the measured closure costs exactly that in a
debug build; against an empty baseline loop `Hex.value` adds none and `JSONString.hex4` adds four per call, one per
iteration of its `for k in 0 ..< 4`. In release all of it is zero and the test passes.

Why the debug loop allocates was not investigated. The fix reads the four digits explicitly (same value, same `nil`);
red then green in AemiJSON, pushed.

A forecast of diary 04 was wrong: AemiJSON's CI would not have turned red on this test. It runs on Linux only, where
allocation counting is unavailable, so it has never measured an allocation budget.
