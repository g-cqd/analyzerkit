# 2026-10-29 (18) — Roadmap 0006: the walker, measured, then built

## Measured first

The probe (aemi `Benchmarks/DirectoryWalk/walk-probe.swift`) walked maintastic, swift-syntax 604 and the 267,000-entry
temporary directory with a stat per entry (today's `SourceDiscovery`), `readdir` with `d_type` by path and by descriptor,
`getattrlistbulk`, and both in parallel. All agreed on every count. Numbers in aemi's diary 2026-10-29-02; the findings:

- `getattrlistbulk`, ADR-0013's choice, reads every entry's inode: barely faster warm, slower cold (130 against 93 ms on
  maintastic, with the vnode cache evicted by walking a directory larger than `kern.maxvnodes`), and 150 times slower on
  the big directory (20.9 s against 134 ms). A first `lstat` there costs 89 µs, a second 2 µs: the cost is the inode.
- Four workers is the knee: readdir on maintastic 31 ms on one, 11 on four, 16 on eight.
- The queue peaks at 440 directories, above launchd's default 256 descriptors, so it holds root-relative paths, opened
  with `O_NOFOLLOW_ANY`, which refuses a link anywhere on the path (checked: plain `O_NOFOLLOW` follows an intermediate one).

ADR-0022 supersedes ADR-0013 on those two points; aemi ADR 0017 fixes the design.

## Built

Another session was writing in aemi's main checkout (new kernel files, untracked), so the walker was built in a worktree
at `/tmp/aemi-walker` on a branch, pushed to `main` as a fast-forward; the other work was not touched. Red (ten tests
against a stub), then green on the first run, then 30 repeats and ThreadSanitizer, all clean. aemi's test targets fail an
expression that takes over 100 ms to type-check, which my first test file did under the machine's load; typed helpers fixed
it rather than a raised budget.

The visited-set plan for links did not survive the tests: in parallel, what it keeps depends on timing. Links are now
never descended, and a link into the root is left to its target. Amended in ADR 0017 before anything used it.
